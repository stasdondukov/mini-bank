# Проверка банковского инварианта

## Запуск

После сборки проекта из его корневого каталога:

```sh
java -cp target/classes bank.ConcurrentBankDemo
java -cp target/classes bank.ConcurrentBankDemo --unsafe
```

Обычный запуск использует внешний монитор `ConcurrentBank` для перевода. В режиме `--unsafe` этот монитор отключён. Клиенты, счета, суммы и число операций одинаковы в обоих режимах. Общая сумма вычисляется до старта потоков и после их завершения.

С этапа 3 операции с балансом отдельного счёта синхронизированы в обоих режимах. С этапа 4 перевод удерживает мониторы обоих счетов, а запись в журнал защищена отдельно. `--unsafe` отключает только внешний монитор `ConcurrentBank`; общий снимок в этом режиме следует получать после завершения клиентов. Таблица ниже содержит результаты этапа 2.

## Объяснение

- Общая сумма без синхронизации сохраняется не всегда. Несколько потоков обращаются к одним и тем же счетам, поэтому при одновременном изменении баланса возможна потеря обновления.
- Shared mutable state — объекты `BankAccount` и их поле `balance`. Также общими изменяемыми данными являются список транзакций в `TransactionJournal` и индекс в `TransactionIndex`.
- Выражения `balance += amount` и `balance -= amount` состоят из чтения старого значения, вычисления нового и записи результата. Проверка доступного остатка с последующим списанием, а также списание и зачисление при переводе тоже являются составными операциями. В случае исключения восстановление старых балансов без блокировки может затереть обновления другого потока.
- Порядок выполнения потоков определяет планировщик. Разные чередования чтений и записей могут привести к разным итоговым балансам при одинаковом коде.
- `join()` позволяет дождаться завершения потоков и увидеть результаты их работы. Он не делает одновременные изменения балансов атомарными. Общая блокировка в `ConcurrentBank` защищает перевод целиком.

## Этап 5. Deadlock

Для эксперимента созданы два счёта по 100 000. Каждый поток выполняет 100 000 переводов по 1 в противоположном направлении.

```sh
java -cp target/classes bank.DeadlockDemo
java -cp target/classes bank.DeadlockDemo --deadlock
```

Обычный режим использует действующий `TransferService`. При проверке 28.11.2026 все пять запусков завершились с одинаковым результатом:

```text
Thread 1 state: TERMINATED
Thread 2 state: TERMINATED
COMPLETED = 200000
INITIAL_TOTAL = 200000.0
FINAL_TOTAL = 200000.0
INVARIANT = true
```

Режим `--deadlock` специально захватывает сначала монитор отправителя, затем монитор получателя. В пяти запусках воспроизведена одна и та же последовательность:

```text
Thread 1 locked A
Thread 2 locked B
Thread 1 waits for B
Thread 2 waits for A
Thread 1 state: BLOCKED
Thread 2 state: BLOCKED
DEADLOCK = true
```

Первый поток удерживает A и ждёт B, принадлежащий второму потоку. Второй удерживает B и ждёт A, принадлежащий первому. Оба смогут выйти из своих внешних блоков `synchronized` только после получения второго монитора. Поэтому ни один из них не может продолжить работу или освободить уже захваченный монитор. Получается circular wait (T1 → T2 → T1).

В `BankAccount.transferTo()` оба направления перевода захватывают мониторы по возрастанию `System.identityHashCode()`. Если хеши совпали, используется отдельный монитор для таких переводов. При едином порядке захвата круговое ожидание между этими переводами не возникает.

Ошибочный режим запускается отдельно и использует два daemon-потока. После фиксации их взаимной блокировки JVM завершает демонстрацию. При обычном запуске оба клиентских потока заканчивают работу, и main дожидается их через `join()`.
